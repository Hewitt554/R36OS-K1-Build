# CP26 — First experimental K1 diagnostic kit, using original R3 image as base

**The original R3 image exists on the user's Windows PC only. Their SD1 is currently unbootable; there is no spare SD or free room for a second raw backup. This checkpoint is designed for that constraint, not for a hypothetical working SD1.**

CP26 uses the Windows user's existing fully checksum-verified 18,375,245,824-byte R3 `.img` as the raw SD1 base. The only full-image write is performed with a trusted, separately chosen image flasher (e.g., Raspberry Pi Imager) directly from that existing file. This kit intentionally avoids building a second copy of the 18.4 GB IMG and **contains no raw physical disk writer**, because we cannot accurately validate host disk enumeration or writes on the user's Windows system. Target disk misselection can destroy arbitrary data. The image will erase the existing SD1; do not attach or choose SD2. The Windows FAT32 BOOT overlay installer is gated on a verified original 5108-byte boot.ini and old BOOT files; refusal means STOP, not manually copy around checks.

The kit uses **actual checksum-verified** K1 Linux 6.12.94 ARM64 `Image` and its Panel4 `rk3326-r36s-k1.dtb` from the rebuilt K1 artifact run **39038977056** artifact **12103773756**; archive SHA256 **d5945b6760df7b52b4036aec3896b9491498fe2b556e48ef253f677407b581d8**. It uses the **actual renewed CP17 arch=ARM 2 diagnostic uInitrd** from successful run **39044552247** artifact **12105631029**, verified by declared SHA256 and Panel4 DTB manifest. CI stages only these few files plus self-contained installer, so the Windows kit is much smaller than the original K1 kernel archive or original R3 image.

`BOOT_PAYLOAD/boot.ini` is a *new, deliberately experimental* script for the **dedicated diagnostic trial only**. It loads Image at `0x02000000`, uInitrd at `0x01100000`, Panel4 DTB at `0x01f00000`, checks all three load return codes, sets `rdinit=/init` with no root filesystem, and calls `booti`. The checked original R3 script was found to execute conditional `fatwrite` and `saveenv` and has unguarded loads, so we do **not** use it as a pretend automatic fallback. CP08 boot gate is retired. The diagnostic is RAM-only and **never intended to write SD**. **This still has no validated real U-Boot acceptance, panel timing, or verified independent recovery; power loss during FAT32 boot file writes is also not proven safe.** A failed trial may present a black screen and/or reboot loop, and the pre-existing non-booting card cannot be assumed to boot with restored R3 boot.ini.

The BOOT-only installer stores the 5108-byte original script in `R3BOOT.BAK`, stage/checksums files in `R36OS/CP26/`, and replaces root `boot.ini` as the **last operation**. The separate restore command can restore original `boot.ini` from the backup when Windows can still mount BOOT; it is not a full-image rollback. Reflash the existing R3 `.img` to restore the original card contents; if that image still fails, the baseline is not working.

The CP06–CP25 source work is cumulative in GitHub, but **this physical kit is intentionally a first-boot diagnostic only**. It does not claim a complete native Debian userland, display stack, Box64, applications, audio, networking, updater, or recovery UI. Once actual hardware results arrive, later checkpoints can add the verified native root integration while keeping the independent native K1 module ABI in sync. False advertising it as a full Alpha6 update would mask the very boot problem the test must isolate.

## Honest validation

- CI: original bootstrap source pins, K1 archive SHA256 and CP13 manifests, CPU Image magic, DTB SHA256 against CP17 report, ARM2 diagnostic header hash, packaging CRC, simulated FAT installer/restore and negative tests.
- **Not validated:** physical Windows flashing or installer on the user's Windows FAT mount; hardware U-Boot version and `booti` success; physical Panel4 display; kernel/device-tree boot; hardware SD1/SD2 separation; recovery after U-Boot persistent environment changes.
- **Explicit next user action:** when a complete kit is available and user accepts erasing nonbooting SD1, verify original R3 IMG, flash SD1 using a trusted existing GUI imaging app, then run the included BOOT installer; photograph/report first screen. If no original .img accessible or BOOT preflight fails, stop.
- All test ZIPs and manifest metadata carry `safe_to_flash:false`, which refers to **unproven boot/recovery readiness**, not to the user's explicit choice to try an experimental image on an otherwise nonbooting SD1.
